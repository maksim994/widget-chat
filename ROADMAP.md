# Roadmap MVP Web Chat Platform

## Цель MVP

Создать web-сервис для коммуникации бизнеса с посетителями сайтов. Клиент может подключить один или несколько сайтов, установить на каждый сайт JS-виджет и вести переписку с посетителями в личном кабинете.

MVP должен закрыть базовый сценарий: посетитель пишет в виджет на сайте, оставляет контакт после первого сообщения, оператор видит обращение в кабинете и отвечает в реальном времени. Если операторов нет онлайн, виджет собирает офлайн-заявку.

## Зафиксированные ограничения

В продукт не входят и не планируются:

- Мобильные приложения.
- Десктопные приложения.
- CRM-интеграции.
- Интеграции с мессенджерами, соцсетями, email, Avito и телефонией.
- Массовые рассылки.

В MVP также не входят:

- ИИ-оператор, ИИ-ассистент и сложные чат-боты.
- Платежи и биллинг.
- Enterprise-роли, сложные SLA и мультибрендовая структура.

## Этап 1. Базовая платформа и аккаунты

Цель: подготовить основу сервиса, на которой будут работать компании, сайты, операторы и диалоги.

Функционал:

- Регистрация и авторизация администратора компании.
- Создание компании.
- Добавление операторов.
- Базовые роли: администратор и оператор.
- Изоляция данных между компаниями.
- Базовая структура данных: компания, сайт, пользователь кабинета, посетитель, диалог, сообщение.

Результат этапа:

- Администратор может войти в кабинет, создать компанию и добавить операторов.
- Оператор может войти в кабинет.
- Данные разных компаний не смешиваются.

## Этап 2. Управление сайтами клиента

Цель: учесть, что у одного клиента может быть несколько сайтов.

Функционал:

- Добавление нескольких сайтов внутри одной компании.
- Настройки сайта: название, домен, активность.
- Уникальный идентификатор сайта для виджета.
- Отдельный код установки виджета для каждого сайта.
- Привязка всех будущих диалогов и событий к конкретному сайту.

Результат этапа:

- Клиент может добавить один или несколько сайтов.
- Для каждого сайта доступен отдельный код установки.
- Система понимает, с какого сайта пришел посетитель.

## Этап 3. Встраиваемый JS-виджет

Цель: реализовать клиентскую часть, которую владелец сайта вставляет на страницу.

Функционал:

- Загрузка виджета через JS-код.
- Кнопка открытия чата на сайте.
- Окно чата с приветствием.
- Отправка первого сообщения посетителем.
- Запрос контакта после первого сообщения.
- Сохранение сессии посетителя в браузере.
- Адаптивный интерфейс для мобильного браузера.
- Базовая кастомизация по сайту: цвет, название, приветствие, позиция, текст офлайн-формы.

Результат этапа:

- Виджет можно установить на сайт.
- Посетитель может открыть чат и отправить сообщение.
- После первого сообщения виджет просит оставить контакт.
- Диалог создается в системе и привязан к нужному сайту.

## Этап 4. Онлайн-чат и сообщения в реальном времени

Цель: связать посетителя сайта и оператора через live-chat.

Функционал:

- Доставка сообщений от посетителя в личный кабинет.
- Ответы оператора из кабинета в виджет.
- Реальное время через WebSocket, SSE или аналогичный механизм.
- Технические статусы сообщений: отправляется, доставлено.
- Индикатор активности оператора.
- Базовая антифлуд-защита и rate limit для виджета.

Результат этапа:

- Посетитель и оператор могут вести переписку без обновления страницы.
- Сообщения сохраняются в истории.
- Система выдерживает базовую защиту от спама.

## Этап 5. Личный кабинет оператора

Цель: дать оператору рабочее место для обработки обращений.

Функционал:

- Список диалогов.
- Фильтры: сайт, новые, в работе, закрытые, офлайн-заявки.
- Карточка диалога: переписка, контакт посетителя, сайт, страница обращения, UTM-метки, время первого сообщения.
- Ответ оператора в выбранный диалог.
- Назначение диалога на оператора.
- Статусы диалога: `Новый`, `В работе`, `Ожидает ответа посетителя`, `Закрыт`.
- Базовый поиск по диалогам и контактам.

Результат этапа:

- Оператор видит все обращения компании.
- Оператор понимает, с какого сайта и страницы пришел диалог.
- Оператор может ответить, назначить диалог на себя и закрыть его.

## Этап 6. Офлайн-режим и рабочее время

Цель: не терять обращения, когда операторов нет онлайн.

Функционал:

- Определение доступности операторов.
- Рабочее время отдельно для каждого сайта.
- Переключение виджета в офлайн-режим, если операторов нет или сайт вне рабочего времени.
- Офлайн-форма с сообщением и контактами посетителя.
- Сохранение офлайн-заявки в общем списке диалогов.

Результат этапа:

- Если оператор недоступен, посетитель видит офлайн-форму.
- Офлайн-заявка попадает в личный кабинет.
- Оператор может обработать заявку позже.

## Этап 7. Настройки виджета и сайтов

Цель: дать администратору базовое управление внешним видом и поведением виджета.

Функционал:

- Настройки виджета отдельно для каждого сайта.
- Цветовая схема.
- Название в шапке виджета.
- Приветственный текст.
- Текст офлайн-формы.
- Позиция кнопки виджета.
- Включение и выключение сайта.
- Просмотр кода установки.

Результат этапа:

- Администратор может настроить виджет под каждый сайт.
- Изменения применяются без переустановки кода, если идентификатор сайта не меняется.

## Этап 8. Интеграция с Яндекс Метрикой

Цель: передавать ключевые события виджета в счетчик Яндекс Метрики сайта клиента.

Функционал:

- Настройка ID счетчика Метрики отдельно для каждого сайта.
- Отправка событий из виджета в счетчик сайта.
- Сохранение URL страницы, UTM-меток и сайта в карточке диалога.
- Базовые события:
  - `chat_widget_shown`
  - `chat_widget_opened`
  - `chat_first_message_sent`
  - `chat_contact_requested`
  - `chat_contact_submitted`
  - `chat_operator_replied`
  - `chat_offline_form_submitted`
  - `chat_dialog_closed`

Результат этапа:

- Клиент может видеть события чата в Яндекс Метрике.
- События отправляются в счетчик конкретного сайта.
- В кабинете сохраняется контекст обращения: сайт, страница и UTM-метки.

## Этап 9. Базовая аналитика в кабинете

Цель: показать клиенту минимальную полезную статистику без сложной BI-системы.

Функционал:

- Количество диалогов.
- Количество лидов с контактами.
- Количество офлайн-заявок.
- Среднее время первого ответа.
- Распределение обращений по сайтам.
- Распределение обращений по страницам и источникам.
- Фильтр статистики по периоду и сайту.

Результат этапа:

- Администратор видит общую статистику по компании.
- Администратор может посмотреть статистику по отдельному сайту.
- Метрики помогают оценить эффективность виджета и операторов.

## Этап 10. Стабилизация и подготовка к запуску

Цель: довести MVP до состояния, пригодного для пилотного использования.

Функционал:

- Проверка основных пользовательских сценариев.
- Логирование ошибок виджета и backend-части.
- Обработка типовых ошибок подключения виджета.
- Проверка прав доступа.
- Проверка изоляции компаний и сайтов.
- Минимальная документация по установке виджета.
- Минимальная документация по настройке Яндекс Метрики.

Результат этапа:

- MVP можно передать первым клиентам для пилота.
- Основные сценарии работают стабильно.
- Есть инструкция по подключению сайта и настройке событий.

## Критерии готовности MVP

- Клиент может зарегистрировать компанию.
- Клиент может добавить один или несколько сайтов.
- Для каждого сайта можно получить отдельный код установки виджета.
- Виджет можно установить на сайт и открыть в браузере.
- Посетитель может отправить сообщение.
- После первого сообщения посетитель видит запрос контакта.
- Оператор видит входящий диалог, сайт и страницу обращения.
- Оператор может ответить в реальном времени.
- Если операторов нет онлайн, посетитель видит офлайн-форму.
- Диалоги, сообщения и контакты сохраняются в истории.
- Диалоги можно фильтровать по сайту и статусу.
- События виджета отправляются в Яндекс Метрику соответствующего сайта.
- Администратор видит базовую статистику по всем сайтам и по отдельному сайту.
